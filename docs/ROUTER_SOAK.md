# Проверка стабильности на роутере

Этот этап выполняется после установки проверенного выпуска. Стенд CI не воспроизводит прошивку ASUS, радиоканал, провайдера и ограничения удалённого Xray.

1. Убедись, что панель открывается, USB подключён и DNS, правила и HTTPS подтверждены. Сохрани отчёт о состоянии до испытания.
2. Подключи одно устройство: воспроизведение YouTube на 10 минут. Запиши задержку и максимальный RSS Xray/панели.
3. Добавь второе, затем третье устройство, по 10 минут на ступень. Используй одно и то же видео/качество, на ПК параллельно скачивай файл. Запиши число клиентов, транспорт, время старта и время каждой ошибки.
4. Оставь три устройства на час, затем при возможности повтори вечером. Следи за доступной RAM, swap, conntrack и ростом задержки под нагрузкой. Не меняй параметры XHTTP посреди одной серии.
5. При сбое сразу скачай отчёт. Сравни прямой интернет, TCP VPN-сервера, DNS helper, DNS Xray и HTTPS. Снимок перед восстановлением поможет отличить отказ сервера от исчезновения локального правила.
6. Если нужно сравнить параметры XHTTP, поменяй один параметр и повтори те же ступени. Сравнивай обрывы и задержку, а не только максимальную скорость.

Для проверки восстановления можно во время отдельного согласованного окна выключить VPN-сервер и включить обратно. Это оборвёт соединения; такой тест не нужен для обычной проверки под нагрузкой. Удалять правила или завершать процессы на рабочем роутере ради теста не требуется.

Условия приёмки: нет необъяснимых рестартов, ошибки одного сайта не перезапускают туннель, после восстановления есть подтверждение DNS/правил/HTTPS, интерфейс остаётся доступен. Без этих измерений нельзя обещать определённую скорость или полное отсутствие обрывов.

## Автоматизированный стенд

В GitHub открой **Actions → Extended network stability → Run workflow**. По умолчанию серия длится 60 минут, допустимо 1–180. Три клиента одновременно передают данные через Linux NAT; один получает медленный DNS. Периодически имитируется сброс upstream, в конце снимается и возвращается hook. Отчёт в Summary содержит раунды, ошибки, p95 длительности раунда и RSS имитированного backend. Исходящий интернет и реальные VPN-ключи не используются.

Обычный CI выполняет 120 секунд нагрузки. Успех этого теста не доказывает стабильность XHTTP или прошивки ASUS.

## Наблюдение за настоящим роутером

На ПК с Python 3 из каталога репозитория:

```sh
python tools/router_soak.py --minutes 60 --output darkls-router-soak.json
```

Введи пароль **панели**, затем создай нагрузку тремя домашними устройствами по методике выше. Раз в 15 секунд скрипт читает статус и метрики; настройки, DNS и процессы не меняет, загрузки сам не запускает. Пароль и cookie находятся только в памяти. В JSON входят только выбранные логические и числовые поля, RSS панели/Xray и доступная RAM. Ctrl+C завершает наблюдение с сохранением отчёта.

Показываются отсутствие подтверждения, неизвестные замеры и последовательности таких замеров. Это не точная длительность обрыва: между опросами события могут оставаться незамеченными. Рост RSS за серию сам по себе не доказывает утечку — сравни одинаковую нагрузку после прогрева. Реальное часовое испытание считается выполненным только после запуска на рабочем роутере.


## Резерв и перезагрузка

Запусти наблюдение с ПК при трёх активных клиентах. До начала проверь основной и резервный профили и запиши, включено ли автопереключение.

| Сценарий | Что считать успехом |
| --- | --- |
| Основной сервер недоступен, прямой интернет работает | На карточке видна причина; панель выбирает проверенный резерв, если он настроен и автопереключение включено. HTTPS через VPN снова подтверждается, приложения возобновляют работу. |
| Основной сервер вернулся | Активный резерв не сбрасывается сам. Ручной возврат проверяет основной профиль перед переключением. |
| Плановая перезагрузка ASUS | Панель снова открывается, правила и оба DNS-входа работают, HTTPS через VPN подтверждён. Если сеанс сброшен, наблюдатель попросит пароль панели и продолжит запись. |

Сбой основного сервера моделируй только в согласованное окно, на тестовом профиле или на сервере, которым управляешь. Отметь момент сбоя и первого успешного запроса с клиента: отчёт фиксирует обнаруженные переключения и перезагрузки, но не точное время обрыва. Сохрани JSON наблюдения и диагностический отчёт после серии.
